## §0 先说三条不好听的实话

这三条会改变你对"极速"的预期，放在最前面，因为它们决定了后面所有选型。

### 0.1 你的机器没有独立显卡

实测：i5-1155G7（4 核 8 线程）+ Intel Iris Xe 核显 + 16 GB 内存。

这意味着**本地 AI 模型的吞吐有硬上限**。实测量级参考（INT8 量化 + ONNX Runtime，8 线程）：

| 任务 | 本机预期速度 | 1 万条素材要多久 |
|---|---|---|
| 中文文本向量化（BGE-small-zh） | 200~500 条/秒 | 20~50 秒 |
| 图片语义向量（Chinese-CLIP ViT-B/16） | 10~30 张/秒 | 6~17 分钟 |
| 图片文字识别（RapidOCR PP-OCRv4） | 5~15 张/秒 | 11~33 分钟 |
| 语音转文字（SenseVoice-small） | 10~30 倍速 | 1 小时音频 ≈ 2~6 分钟 |
| 视频（抽关键帧 + 转录） | 5~15 倍速 | 1 小时视频 ≈ 4~12 分钟 |

**所以"极速"必须拆成两件事，否则一定会失望：**

- **检索极速** —— 做得到，而且是真的极速：**首屏结果 < 80 毫秒**（10 万条规模）。这是索引建好之后的事，跟显卡无关，跟数据结构有关。
- **分析不是极速，是"并发 + 后台 + 无感"** —— 一次投喂 1 万张图，物理上就是要十几分钟。能做的是：**多进程吃满 CPU、优先处理你正在看的、断点续跑、跑的时候界面不卡一帧、跑完通知你**。

> 我的建议：把验收标准写成「**检索 P95 < 200ms**」+「**分析吞吐 ≥ N/秒且全程 UI 不掉帧**」，而不是笼统的"极速"。
> 想突破这个上限只有两条路：换台带 NVIDIA 显卡的机器，或者把重活交给云端 API（见 A 组选型）。

### 0.2 「搜索消息」这四个字有个雷

如果"消息"指的是**微信/QQ 的聊天记录**：这些数据库是加密的，解密要读取运行中进程的内存密钥。技术上做得到，但**属于绕过软件保护措施**，且微信客户端更新一次就可能全盘失效。

我的处理：**默认不做聊天软件数据库的破解读取**。替代方案（都是合规且稳定的）：
- 微信/QQ **手动导出**的聊天记录文件（txt/html/csv）→ 正常解析索引 ✅
- Telegram 官方 JSON 导出 ✅
- 邮件（IMAP 只读）、Slack/Discord 官方 API ✅
- 系统通知历史、剪贴板历史 ✅

如果你要的"消息"其实就是"信息/内容"，那这条不适用，当我没说。**Q1 会问清楚。**

### 0.3 已经有现成工具能覆盖一部分，我先摆出来

按 V 类价值提问的规矩，我必须主动给你更省事的路，哪怕它会让我这边工作量变小：

| 现成方案 | 覆盖了什么 | 缺什么 |
|---|---|---|
| **Everything** | 文件名瞬时搜索，毫秒级 | 不看内容、不懂语义 |
| **Immich / PhotoPrism** | 照片语义搜索 + 人脸聚类 | 只管照片，不管文档/链接/视频 |
| **Karakeep（原 Hoarder）** | 网页链接收藏 + AI 打标 + 全文搜 | 不管本地文件 |
| **Recoll / DocFetcher** | 本地文档全文检索 | 关键词匹配，无语义、无多模态 |

**它们的共同缺口，也就是 Synorive 真正值得存在的理由：**
① 没有一个把 本地文件 + 网页 + 消息 + 视频 **统一到一个索引里**；
② 没有一个能**跨模态互搜**（用图找文、用文找视频里的某一秒）；
③ 没有一个能被 **Claude Code 直接调用**当成 AI 的长期记忆库；
④ 没有一个是**中文优先**的（大部分开源方案的中文语义检索效果明显打折）。

如果你只要①，那装 Karakeep + Immich 两个 Docker 容器，一下午就完事，不用做这个项目。
**如果你要的是②③④，那这个项目就是值得的。Q1 会请你确认。**

**为什么引擎要独立成一个进程**：Electron 的 JS 主线程一旦被计算占住，整个界面就卡死。把分析全部隔离到另一个进程，**界面卡不卡跟引擎忙不忙彻底解耦**——这是「使用时不卡顿」这条要求唯一可靠的实现方式，不是靠优化代码写得快。

## §2 检索为什么能做到 80 毫秒

不是靠堆硬件，是靠**三级瀑布 + 流式返回**：

```
你敲下第一个字
  ├─ 第 0~15ms   前缀索引命中最近打开过的 → 立刻显示（0 延迟感）
  ├─ 第 15~50ms  SQLite FTS5 关键词召回 Top200 → 追加显示
  ├─ 第 50~150ms sqlite-vec 向量近邻召回 Top200 → 融合去重、重新排序
  └─ 第 150~400ms（可选）重排模型精排 Top20 → 悄悄换序，不闪屏
```

关键点：**结果是"长出来"的，不是"等出来"的**。你永远在第 15 毫秒就看到东西，后面的结果平滑插进来，不清屏、不跳动、不转圈。

融合算法用 **RRF（倒数排名融合）**——关键词和语义两路各自的排名倒数相加，不需要调分数量纲，工程上最稳。

## §3 界面与字体规范（严格按你的要求）

### 3.1 字号对照表（中文字号 → CSS 像素，Windows 下 1pt = 1.333px）

| 中文字号 | pt | CSS px | 用在哪 |
|---|---|---|---|
| 二号 | 22 | **29.33px** | 应用主标题、启动页品牌名 |
| 小二 | 18 | **24px** | **界面主标题**（如「文件管理器」「分析中心」）★你点名的那个 |
| 三号 | 16 | **21.33px** | 区块标题、功能分区名 |
| 小三 | 15 | **20px** | 次级标题、卡片主标题 |
| 四号 | 14 | **18.67px** | 重要正文、主要按钮、搜索框输入 |
| 小四 | 12 | **16px** | **正文默认**、列表项、说明文字 |
| 五号 | 10.5 | **14px** | 辅助信息、状态栏、时间戳 |

### 3.2 中英混排怎么实现

```css
:root{
  --font-body: "Times New Roman", "SimSun", "宋体", serif;
}
```

**把 Times New Roman 放第一位**，浏览器按字符逐个回退：拉丁字母、数字、西文标点（. , ; : ' " ( ) ?）从 Times New Roman 取字形；汉字和中文全角标点（，。、「」）Times New Roman 里没有，**自动回退到宋体**。一行 CSS 就精确实现你要的效果，不需要写 JS 逐字符切换。

### 3.3 一条必须告诉你的实话：宋体在大字号下会掉档次

Windows 自带的 **SimSun 宋体是为屏幕点阵设计的老字体**。16px（小四）正好是它的原生点阵尺寸，非常清晰；但到了 **24px 以上（界面主标题），SimSun 的轮廓会显得又细又硬，反而不高级**。

三个处理办法，你选（见 F 组 F1）：
- **F1-a**（默认，完全按你说的）：全用 SimSun，大标题加字重/字距补偿
- **F1-b**（推荐）：正文 SimSun 不变，**只有大标题换思源宋体 Source Han Serif**——同为宋体骨架，视觉统一，但大字号下质感高一个档次，字体随应用打包不依赖系统
- **F1-c**：全部换思源宋体

### 3.4 视觉方向：学术工作台

既然定了宋体 + Times New Roman，这套字体天生带**书卷气/学术气**。所以整个界面的方向应该是"**专业工作台**"而不是"科技感炫酷 UI"——后者配衬线字体会非常违和。

- **底色**：暖白纸感 `#FAF9F6`（不是纯白，长时间看眼睛不累）／深色模式用暖灰 `#1C1B19`（不是纯黑，避免 OLED 眩光和文字光晕）
- **主色**：一个低饱和的墨蓝 `#2B4C6F`，只用在真正需要注意的地方（选中态、主按钮）
- **强调色**：朱砂红 `#A8342A`，只用于删除/警告，全应用不超过 3 处
- **不用**：渐变、霓虹、玻璃拟态、大圆角、彩色阴影——这些和衬线字体是打架的
- **层次靠留白和一条 1px 的细线做**，不靠颜色堆叠

### 3.5 重要功能放在重要位置

界面主轴按"**你 90% 的时间在干什么**"排：

```
┌─────────────────────────────────────────────────────┐
│  ⌘  Synorive        [ 🔍 搜索一切… 或把文件拖到这里 ]  │ ← 全局搜索框永远在顶部中央
├──────┬──────────────────────────────────────────────┤   （最重要的功能，最重要的位置）
│ 侧栏 │                                              │
│ 收窄 │           结果区 / 分析区                     │
│ 64px │           （唯一的主舞台）                     │
│ 图标 │                                              │
│ +文字│                                              │
├──────┴──────────────────────────────────────────────┤
│  状态栏：索引进度 · 队列 12 · CPU 45% · 已索引 8.2万  │ ← 后台在忙什么永远可见，不打扰
└─────────────────────────────────────────────────────┘
```

- **搜索框全局唯一、永远可达**（任何界面按 `/` 或 `Ctrl+K` 直接聚焦）
- **拖拽区就是搜索框本身**——拖文件进去 = 用这个文件反查相似内容，不用先找"上传"按钮
- 侧栏最多 6 个一级入口，多了就是没想清楚
- **界面统一靠"设计令牌"强制**：所有颜色/字号/间距/圆角/动效时长都从一个 `tokens.ts` 取，**代码里禁止出现硬编码的色值和像素数**，做不到统一是机制问题不是自觉问题
